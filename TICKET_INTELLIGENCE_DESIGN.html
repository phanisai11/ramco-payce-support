Attachment rules

  • Server-generated attachment UUID; customer filename is metadata, never an object path.
  • Original is created once with ifGenerationMatch=0; hash + GCS generation go in an append-only manifest.
  • Unresolved identity → regional intake quarantine. Resolved → tenant-bound raw path. Only StorageBroker can read it.
  • Max size/type/decompression limits and malware/DLP scan before processing. Only redacted derivatives and extracted fields go downstream.

Join semantics

All processors run in parallel. Workflows waits up to a timeout and merges versioned results into ticket.evidence[]. Malware/DLP failure or tenant mismatch blocks the attachment and forces human/security handling; a non-security processor gap may continue as human_only. No failed scan is treated as safe.

Contract rules

  • Raw is immutable. Original event/file is created with ifGenerationMatch=0; hash + generation are recorded. Runtime roles cannot update/delete it.
  • Tenant bound. Server-derived tenant_id is present in every tenant row, object namespace, cache key and decision. Callers never provide object paths.
  • Masked by construction. No field after intake can hold a raw identifier. A schema validator rejects it.
  • Provenance on derived fields. Each derived value records the rule or model version that produced it.
  • Strict, versioned schema. Reject unknown top-level fields, invalid enums/timestamps, missing hashes, size/count violations, and tenant-mismatched attachment manifests.
  • Idempotent. Keyed on ticket_id + source event id. Replaying an event never creates a second ticket.
  • No in-place correction. New customer input creates a new event; a normalization fix creates canonical_version + 1; routing decisions supersede, never edit.

Storage split

  • Cloud SQL: append-only manifests, canonical events and routing decisions; current state is a rebuildable projection. Composite tenant foreign keys + FORCE RLS.
  • BigQuery: every version of the canonical ticket (analytics, evaluation sets, replay; never used to train models).
  • Regional GCS cells: unresolved quarantine · tenant-bound immutable raw · separately versioned redacted derivatives. Reads only through StorageBroker.

5 · Multi-axis classification (not one label)

Why one "category" fails: in Q3, 57 tickets moved with the reason "Not payroll – moving to compliance", 125 were "wrong team/queue" and 57 were "re-categorised". A PF-ceiling payslip ticket is at once Payroll (symptom), Statutory (cause), Defect (PNJ-4412) and Pay-at-risk (impact). A single label forces a choice, and the choice becomes a reassignment. We classify along independent axes and route on the combination.

how-to / questionproblem / suspected defectchange requeststatus enquiryrefund / billingcomplaint / escalationaccess / securityfeedback
Separates "how do I…" from "it's broken". Many "How-To"-labelled tickets in Q3 were really defects (later Jira-linked).

5A · How-to RAG: region + effective time + ticket timing

L7 retrieval is not global semantic search. Chunks are partitioned and filtered so IN and UAE content, and pre/post rule-change text, cannot be mixed in one retrieve. Barnett et al. (CAIN 2024, DOI 10.1145/3644815.3644945) list failure modes such as missing context, wrong rank, consolidation dropping the right chunk, and contradictory context — region + t_as_of filters and small top-k directly reduce those.

DimensionRule
RegionRetrieve only within the ticket tenant’s region (IN vs UAE). No cross-region chunks in one query.
t_as_ofIf L1 extracted a payroll period, use the end-of-month (or payroll-close) UTC for that period as t_as_of. Else use latest customer message time (UTC) from the canonical ticket. Cap at now_utc. Statutory values still come only from the engine (L4), not from chunks.
Validity windowRequire valid_from ≤ t_as_of < valid_to (or valid_to null = open-ended). Excludes KB-0142-style stale articles after rule change.
Arrival periodTag payroll week (25th→3rd): stricter retrieval (smaller top-k or higher τ), prefer template/status/engine paths — per PRODUCTION_DESIGN_GCP.md §2A.
Revised questionOn a new customer message, recompute t_as_of from the latest turn so “actually August” changes the filter.

7 · Classification cascade: rules first, triage default

Raw export categories are unreliable. Auto-route requires a rule id in routing_policy/approved.yaml with G3 ≥99% on holdout. See eval/datasets/README.md.

① Hard rulesP1, injection, refund, error codes, file type, region — immediate lane/queue when rule matches approved pack.
② Policy tablesMined offline from human routing_gold.jsonl; each row shipped only if precision ≥99%.
③ Offline scorer (optional)Versioned artifact from gold; not neighbor search. auto_route if p≥τ and G3 manifest allows.
④ Consistency checksStatutory domain ⇒ region; pay-at-risk ⇒ raise priority; risk ⇒ no auto-route.
⑤ Suggest (optional)Flash closed-label hint for sidebar — never writes queue.
⑥ TriageDefault. Agent pick → rule_candidate queue for weekly promotion, not live vector index.
# per-axis decision (production — rules / policy / offline scorer only)
def classify(t):
    out = {}
    hard = rules.match(t)                      # ①
    policy = policy_table.match(t)             # ② approved rows only
    for axis in AXES:
        if axis in hard and hard.rule_id in G3_APPROVED:
            out[axis] = (hard[axis], 1.0, "rule:"+hard.rule_id); continue
        if policy and policy.rule_id in G3_APPROVED:
            out[axis] = (policy[axis], 1.0, "policy:"+policy.rule_id); continue
        scorer = offline_scorer.predict(t)     # ③ optional artifact
        if scorer and scorer.p >= TAU and scorer.row in G3_APPROVED:
            out[axis] = (scorer.label, scorer.p, "scorer"); continue
        out[axis] = (None, 0, "triage")       # ⑥
    out = consistency.apply(out, t)            # ④
    return out

  • 99% accuracy applies to tickets where auto_route=true, not to every suggestion.
  • LLM confidence is capped at 0.85. decided_by=llm cannot set auto_route=true.
  • The LLM cannot invent a label outside the candidates (closed set), except for open axes like sentiment.
  • Priority can only be raised by the derived logic, never lowered below the customer's choice without an agent.

  • Operational KPI: LLM suggest ≤5%/month; grow approved rules, not vector indexes.
Re-classification is continuous, not one-shot. Re-run the cascade on: a new customer message, a new attachment, a Jira link, a matching incident opened, or a rule change (e.g. 1 Aug PF). A label change emits ticket.reclassified with a reason, so routing is updated with a logged reason rather than a blind reassignment.
Routing evidence is immutable. Each evaluation writes a new routing_decision with tenant_id, event_id, canonical_version, input fingerprint, policy/rule version, lane, queue, reason codes and timestamp. A later result uses supersedes_decision_id; it never edits the earlier decision. auto_route=true additionally requires resolved tenant, schema pass, no blocking risk and a G3-approved rule/scorer row. Ordering within a pool

Score = SLA time remaining⁻¹ × tier weight × impact weight × (1 + reopen). Uses the Schedule 3 clock (pause only on "Pending – customer"), so the queue is ordered by contractual and credit exposure, not arrival order.

Anti-bounce controls

  • Ownership sticks: shift handover keeps the owner pool and adds a handover note (112 Q3 handovers re-queued tickets).
  • A 2nd cross-pool move needs a lead's approval plus a reason code from a closed list (no blanks; 106 were blank in Q3).
  • Every reassignment adds a rule_candidate and eval case for weekly rule promotion — not vector neighbor routing.
  • KPI: % of tickets resolved in the first pool (Q3 baseline: ~85%; 204 ended elsewhere).

Capacity

Roster (42 agents: Pune 25, Bengaluru 11, Dubai 6), shift calendar and language skills live in Cloud SQL. Routing respects who is on shift now.

10 · Beyond tickets: removing demand, not just handling it

🔔 Rule-change radar

When a statutory rule version is published, find the tenants with affected employees, runs in the window and outdated KB citations. Then (a) push a notice, (b) mark the KB stale, (c) pre-load answer path A. In Q3, KB-0142 and KB-0201 caused 23 reopens after their effective dates.

📡 Customer-facing run tracker

Webhook-driven status of each payroll run, payslip batch and bank file per tenant. It removes "where is my run / refund?" contacts entirely, and the customer stops needing to raise a ticket.

🧭 Product feedback loop

Weekly clusters of how-to subjects → Product backlog with volume and cost. "Bulk payslips", "salary component" and "bulk employees" are UX gaps, not support work. Track the volume drop after each fix.

🧑‍🏫 Active learning from agents

Overrides become rule_candidate rows, eval cases, and approved templates — reviewed weekly into routing_policy. No live ticket index for routing.

🚨 Incident-first console

Agents see live clusters ("12 payslip tickets in 20 min, 3 tenants") before individual tickets. Turns 35 separate replies into one incident + one broadcast.

🧾 Pre-submission validators

Expose the SIF/ECR/bulk-sheet validators inside the product before upload. A defect caught at upload is a ticket that never exists.

🗣️ Voice = transcription, not a bot

Voice notes are transcribed and summarised for agents in AR/Urdu/Malayalam/Hindi. No synthetic voice reply on payroll money topics; customers asked for humans on money.

🤝 Partner-aware intake

Partners (RS-01..09) get a structured form with required fields (tenant, period, run_id, file). This fixes the partner schema at the source instead of normalising it forever.

📸 Guided capture

When a customer starts attaching an image, ask "error screen or payslip?" and blur IDs on the client before upload. Less PII enters the boundary.
